017-per-reviewer-run-settings/Q-1

The retune recipe can lose the retune, and a stale copy gives no signal

Blocks the goal

raised 2026-10-12 14:00 UTC

The spec cannot be called ready while a documented install mode destroys the retune it describes; the walkthrough accepted the stale-copy cost, so this reopens that acceptance.

The problem

Spec 017 tells a reader to copy a shipped reviewer file into their project and edit it, but says nothing about the install that overwrites that copy, about a copy going stale, or about the extra keys such a file can carry.

Why it matters

The chorus review (five lenses, 34 entries) converged on a small set of zero-code fixes. In a per-project install the shipped file and the copy are the same path, so an installer run with --force erases the retune. A copy never learns the plugin moved, and no stamp says which version it was taken from. Three of the findings went to red after voting: the --force erase, the missing version stamp, and silent staleness with no named symptom. All fixes are sentences in the README section and two tasks; no code.

Evidence

  • Codeinstall.sh:21-22The documented per-project install sets the Claude home to the project's own .claude folder.
  • Codeinstall.sh:101-105--force copies over any existing file with no warning; without it an unrecorded file is skipped (line 116).
  • Documentspecs/017-per-reviewer-run-settings/spec.md:74The stale copy is called the accepted cost, with a manual re-compare as the only control.
  • Documentdocs/reviews/2026-10-12-chorus-review.mdThe record: F32, F16 and F12 at red, with four of four, three and two voters confirming.

How it works today, and why that is a problem

A reader copies a shipped reviewer file to the project folder and edits its model, effort or tools. The installer never looks at that copy in a global install. In a per-project install the installer writes the same path, so a rerun skips an unrecorded copy, keeps an edited recorded one, and replaces either with --force. The functional requirement asking for a reason comment says nothing about the plugin version, and the re-compare step names no command and no source path for the shipped file.

Why that is wrong

A reader following the recipe can lose the retune with one flag, cannot tell how old a copy is, and cannot tell that a round failing validation is the stale copy's fault. The person who carries that cost is the newcomer, not the author who accepted it.

Where it should end up

The recipe names both install modes, requires the shipped version in the reason comment, gives one diff command with the source path, names the staleness symptom, and warns about --force, privileged keys, committed copies, the public memory folder and keeping the Write tool.

Options

1

Fold the agreed fixes into the requirements and tasks T001 and T003

Recommended

Edit the reason-comment requirement and the cost statement in the spec, and the two tasks, to carry the stamp, the diff command, the symptom, the per-project warning and the privileged-key and memory sentences.

Work
Edits to the requirements for the reason comment and the cost statement, and to tasks T001 and T003; a re-read of the plan's risk table. No code.
Risk
The README section may grow long enough that newcomers skip the warnings (see 017-per-reviewer-run-settings/Q-2 (README length)).
2

Leave the spec as it is and accept the cost

Alternative

The spec stays as accepted in the walkthrough; the findings stay in the review record only.

Work
Nothing.
Risk
A newcomer can lose a retune with --force and a stale copy fails silently.
